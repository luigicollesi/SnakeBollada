# Food Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement Food Mode as a reusable current-state decision component backed by one centralized Snake×Food route analysis per state, and replace the existing per-food BFS path selection in `basic-v1` without implementing the future-search graph yet.

**Architecture:** Introduce shared movement primitives, a centralized `StateAnalysis` that runs one BFS per live snake and derives all Snake×Food routes plus food-claim competition, then make `FoodMode` consume only that analysis and return at most two candidate first moves. The current `strategy::choose_move` becomes a transitional adapter: it builds `StateAnalysis` once, asks Food Mode for candidates, applies the existing immediate safety/flood-fill checks, and falls back to the existing survival behavior.

**Tech Stack:** Rust 1.98.1, existing `BoardMask`, `VecDeque` BFS, standard library collections, existing Rocket service; no new crate dependencies.

**Spec:** `docs/specs/food-mode.md` (with shared contracts from `docs/specs/decision-making.md`)

## Global Constraints

- Food Mode MUST NOT execute its own Snake→Food BFS.
- Each analyzed state MUST centralize routes for every live snake to every known food.
- Route analysis MUST preserve every first direction that belongs to a shortest path, not one arbitrary parent.
- Food Mode returns at most two candidates and prefers distinct first directions when useful.
- Food competition uses route distance from all live snakes; a nearer-but-losing food must not automatically outrank a farther claimable food.
- Food Mode contains no aggression weighting, border/corner policy, head-to-head policy, future-graph cache, timeout logic, or E2E route scoring.
- Food benefit is not awarded by Food Mode; `AteFood` remains a future Decision/TurnResolver event.
- Central route analysis treats hazards as traversable geometry in this slice; immediate hazard preference remains in the transitional strategy adapter until Decision/Survival owns it.
- Other snakes' tails remain blocked in centralized route analysis. The source snake's current tail may be released only when its final body coordinate is not stacked on the previous coordinate.
- No new dependencies are added.

## Review Focus

- Equal-length shortest routes to one food must union and propagate all first-move bits instead of losing an alternative.
- A geometrically close food that another snake reaches sooner must lose to a farther clearly claimable food when both are otherwise reachable.
- If the two best foods share one first direction, Food Mode should prefer a useful third food with a different first direction rather than return duplicate directional choices.
- Tail handling must not make a stacked source tail passable or an uncertain opponent tail passable.
- No-food, unreachable-food, and enemy-unreachable-to-food states must return stable deterministic results without panics.

- [ ] **Step 4: Implement the per-snake BFS route field**

In `src/analysis/routes.rs`, implement an internal route field with:

```rust

    distance: Vec<u16>,
    first_moves: Vec<MoveMask>,
}
```

Add:

```rust
fn build_route_field(state: &GameState, snake_id: &str) -> SnakeRouteField;
```

Algorithm requirements:

1. Build static occupied cells from all current snake bodies.
2. Unblock the source snake head.
3. Unblock only the source snake's final tail coordinate when the last two body coordinates differ.
4. Keep every other snake tail blocked.
5. Hazards remain traversable in this centralized geometric analysis.
6. BFS by cardinal moves.
7. When a shorter path reaches a cell, replace its distance and first-move mask.
8. When an equal-distance path adds new first-move bits, union the mask and re-enqueue that cell so the newly discovered first-move alternatives propagate to descendants.

- [ ] **Step 4: Implement deterministic candidate expansion and ranking**

For each known food:

1. read our `FoodRouteInfo`;
2. skip unreachable routes;
3. expand each bit in `first_moves` into a candidate;
4. attach `FoodClaimInfo`;
5. deduplicate by first direction, keeping the best food for that direction.

Use a deterministic lexicographic rank:

1. claim class: uncontested/positive margin first, exact contest second, negative margin last;
2. shorter distance;
3. larger claim margin within the same class;
4. `Direction::rank()`;
5. stable food coordinate ordering.

Then sort the best-per-direction candidates and return at most two.

Do not inspect borders, corners, aggression, or future depth.

## Deferred to Decision Making

This plan intentionally does **not** implement:

- FutureGraph / rolling horizon;
- depth 3+ search;
- action-joint simulation;
- TurnResolver;
- `InstantEvent::AteFood`;
- food-spawn validation/invalidation;
- provisional E2E route discounting;
- aggression weighting;
- Hunting/Survival route aggregation;
- reserved edge/corner policy.

The interfaces introduced here are designed so those features consume `StateAnalysis` and `FoodModeOutput` rather than replacing them.
